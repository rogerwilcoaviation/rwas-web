# Service intake backend

Dedicated D1 binding: `INTAKE_RECEIPTS`. Apply `migrations/intake/0001_receipts.sql` ONLY to that database. This code does not create infrastructure, migrate a remote database, schedule itself, or send during intake.

Required environment (no defaults): `INTAKE_DISPATCH_SECRET` (cryptographically random, >=32 characters; provision at least 32 random bytes), `RESEND_API_KEY`, `CONTACT_FROM_EMAIL`, `CONTACT_TO_EMAIL`; intake additionally requires `TURNSTILE_SECRET_KEY`. Sender/recipient must be the actual approved fixed mailbox configuration. These are operator configuration, never customer fields. Production Turnstile must issue action `service_intake` for exact hostname `www.rogerwilcoaviation.com` or `rogerwilcoaviation.com`. Preview origins deliberately fail closed. No development/debug verification bypass.

POST intake accepts JSON name/email/message, optional string phone/aircraft, consent true, UUID requestId, Turnstile token and empty optional website. Normalized name <=120 UTF-8 bytes; email <=254; phone <=40; aircraft <=160; message 10 characters–8000 bytes; complete streaming body <=16384 bytes. Returns committed receiptId/receiptToken/status at 202; exact replay returns 202, changed content under same UUID returns 409. A verified original replay does not require re-consuming its single-use Turnstile token; the secret HMAC token is recoverable only with the UUID AND exact normalized submitted payload. Token is 256-bit HMAC with distinct scope; only SHA-256 token hash is stored. Save token privately, not in URLs, analytics or logs. GET receipt requires Authorization Bearer token and returns minimal public status only, no PII/provider ID. No claim of delivery confirmation.

Dispatch POST requires Authorization Bearer `INTAKE_DISPATCH_SECRET`, hash comparison with fixed-loop equality. Parent-owned scheduled Worker should invoke once per five minutes, await the response, and alert on non-2xx without logging bearer headers. This backend drains at most five network attempts per call. Terminal cleanup additionally marks at most five expired rows. Each row gets a two-minute unique lease and fenced completion update; 15-second fetch timeout; attempts durably recorded before network I/O. A crash after claim conservatively consumes an attempt/capacity. Six attempts maximum; exponential 60s to 1h delay, respecting larger Retry-After. Network ambiguity reuses identical persisted JSON and Resend idempotency key. Sender/recipient/body are snapshotted at commit, so environment edits do not mutate retry payloads. Configuration revocation requires stopping dispatch and operator review of queued rows.

Resend retains idempotency for 24h; automatic attempts stop 23h after the first persisted attempt. Rows reaching that boundary enter `needs_review`; exhausted attempts/permanent errors enter `dead_letter`; HTTP409 enters `needs_review`. Operator must reconcile provider evidence before manual action; never blindly reset timestamps or replay terminal rows. Provider acceptance persists provider ID and `provider_accepted`, NOT delivery. No automatic terminal-row redrive, customer copy, Teams, WhatsApp, agents, shell, or QMX integration.

UTC daily admission cap 50; same hashed IP five admissions/hour and twenty verified new-intake requests/hour. Dispatch has a separate UTC-day ceiling of 50 persisted network attempts, including retries/failures, not merely 50 accepted messages. This deliberately conservative cap can defer queued mail and does not guarantee zero cost across existing account services or request/storage usage. D1 serialized write transactions enforce the caps under concurrency. D1 default primary access is used (no read-replica sessions).

PII lives in receipt payload and immutable email JSON; rate guard stores keyed IP hashes. There is intentionally NO automatic retention/deletion policy until owner decides. Database/backup access remains sensitive. No customer/provider error bodies are logged or returned. Secret rotation keeps previously issued receipt tokens valid (stored hashes) but prevents old POST replays from regenerating the same token: those fail 503 rather than returning an unusable token. Plan rotation/recovery with owner; do not casually rotate this shared dispatch/receipt derivation secret.

## Offline verification

From repository root: `node --test tests/intake/backend.test.mjs`. Uses installed Miniflare/workerd real local D1 for migration, transactions, concurrent claims and caps; only Turnstile and Resend HTTP are mocked. No real database or email. Tests include rollback-trigger injection, malformed/types/byte limits, replay/conflict, hashed receipt authorization, auth fail-closed, fixed plaintext provider payload, attempt-before-I/O, concurrency, unknown retry, Retry-After, expiry, dead-letter and caps. Actual production bindings, Turnstile, scheduled dispatch and provider delivery need separately authorized verification. Existing production contact endpoint is untouched.

## Isolated staging exception

Staging requires the exact destination origin `https://intake-restoration-20260922.rwas-web.pages.dev` in every intake/config/dispatch/receipt handler and the advanced-mode wrapper. Intake additionally requires its matching Origin header. Production, deployment-hash and other branch aliases cannot use staging bindings.

Staging permits **one reserved provider attempt total**, not one logical idempotent email with retries. Claims require a queued row, attempts=0 and an empty attempt ledger. Any uncertain response (timeout, malformed success, HTTP 408/429/5xx) becomes needs_review; expired sending leases and previously reserved attempts become needs_review without sending again. A crash before network I/O conservatively consumes the authorization. Production retries remain unchanged.

For builds whose CF_PAGES_BRANCH/GITHUB_HEAD_REF unambiguously identify this exact staging branch, the artifact appends a wildcard noindex/nofollow `_headers` rule preserving existing headers; this covers static paths excluded from the Worker. Other/unknown/conflicting branch builds do not modify headers. Cloudflare Pages also documents automatic preview X-Robots-Tag: noindex (https://developers.cloudflare.com/pages/configuration/preview-deployments/#preview-indexing-by-search-engines). Parent must verify actual deployed headers on static assets, exclusions and normal pages; local tests do not prove platform delivery.
