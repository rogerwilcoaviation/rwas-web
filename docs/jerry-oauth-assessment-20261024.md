## Supported scope versus this website

Official documentation supports subscription sign-in for a person's Codex use. That is distinct from API-key usage and has different data/admin controls. The actual subscription/workspace settings were not verified here. [Codex authentication](https://learn.chatgpt.com/docs/auth).

The newer Sign in with ChatGPT plan-usage documentation covers open-source/local applications and directs paid/remotely hosted applications to an interest form. It binds registration to a user/workspace. A locally running relay receiving public website requests is still serving remote visitors; its physical location alone does not establish that the integration fits the documented local-app scope. [SIWC overview](https://developers.openai.com/siwc/token-sharing-open-source).

The SIWC terms prohibit **“Using one user’s subscription to fulfill another user’s requests.”** Consequently the new SIWC flow is not a supported pooling mechanism for anonymous/seller requests through John's account. This does not establish a categorical ban on every Codex automation or decide which legacy Codex terms apply to the existing OpenClaw transport; that applicable-plan permission is still an evidence gap. [SIWC terms, sections 1–4](https://openai.com/policies/sign-in-with-chatgpt-terms/).

SIWC's documented HTTP path requires streaming and `store:false`, rejects several fields used by the paused direct responder, and can still retain local app-server thread history. It is not a drop-in bearer substitution into that responder. `store:false` does not verify deletion of local history or actual subscription data controls. [Preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).

## Result and remaining decision

**No verified supported public multiuser subscription-backed website option was established.** John's existing local Codex sign-in remains a documented option for his own local work; it is not evidence that visitors' requests can use his plan. Do not route the new account-aware website assistant to the old relay, change credentials, select an unverified Luna alias or silently fall back.

The next architecture decision needs either provider confirmation explicitly covering this exact public multiuser deployment and applicable existing plan, or a user-owned integration design within documented scope (which would change the product experience and still need separate approval). Even with entitlement settled, the inspected relay needs independently proven website-only tools/context, verified owner/surface/session fencing and a complete retention/deletion domain before private chat can be routed through it. No credential or live-model test is requested by this report.

The [provider-neutral alarm fixture](jerry-alarm-probe-local-20261024.md) proceeds separately. Its synthetic cleanup tests do not resolve subscription entitlement or relay privacy gaps.
