# Aviation Exchange activity log

The administrator workspace has a read-only **Activity log** section. It covers the Aviation Exchange marketplace, its account and listing APIs, authentication/security operations, customer support, administrator operations, completed Jerry research, and browser interactions on `/aircraft-for-sale` and its listing pages. The rest of the website is excluded. Existing moderation audit records retain their original behavior; historical browser activity cannot be reconstructed. Logging starts at deployment.

## Fields and troubleshooting

Events contain a server timestamp, account ID/email when verified, action, result, source, HTTP status and duration when applicable, a server-generated request ID, route template, related listing/account/ticket ID, and selected structured operation details. A full-width detail panel shows the UTC timestamp, request ID, conversation thread and review evidence when present. Bulk table responses omit full transcripts/reviews; these load on demand through a separate protected detail endpoint. Table times use the administrator's local timezone; date filters use UTC. Search accepts account email/ID, action, request ID or record ID. Result/source/event-type filters, date bounds, refresh and cursor pagination are available. The existing-report loader searches current account/listing recommendations, including reports made before activity snapshots existed. Current saved reports and historical snapshots are labeled separately.

Server requests carry `X-RWAS-Request-ID` and `X-RWAS-Activity-Recorded`. Authentication responses carry a request ID; their metadata is queued through the private service binding. A failed request is logged independently of business rollback. A server success means that HTTP operation succeeded: it is not proof of a downstream email's delivery, a completed aircraft transaction, or a listing's approval. A `changes` detail on a failed request describes attempted operations; the failure result remains authoritative. Browser events are explicitly labeled as browser reported; they never constitute an authoritative approval or completed mutation.

Browser tracking records page views/leaves, control selection, field changes without contents, form submissions, draft step transitions, Jerry chat transport results and network/client errors. It is mounted only on marketplace pages, stops outside the marketplace after client navigation, and sends small bounded same-origin batches. Browser collection requires JavaScript and connectivity, uses a bounded in-memory queue and cannot guarantee delivery after abrupt process termination. No keystrokes or sign-in form contents are collected. The owner explicitly enabled marketplace conversation retention for troubleshooting: listing-intake exchanges store the visible last question and actual server reply; general chat stores bounded, browser-reported question/reply pairs from the existing chat response, including streamed replies and failed attempts without inventing assistant answers. New turns are grouped by a random conversation ID and verified account. Account references captured at event time are checked against the current verified server identity; unmatched queued events remain unverified after an account switch. During initial hydration, a verified existing cookie resolves the account even before a client account reference exists. An explicit sign-out remains anonymous; unknown historic browser activity is labeled account not recorded instead of asserting that it was signed out. No historic anonymous rows are guessed or reassigned.

## Access, data handling and storage

`GET /api/aircraft-sale/staff/activity`, its event-detail route and `/current` report route require the existing current verified administrator identity, including the established MFA policy. The legacy `/admin/activity` route requires the scoped account administrator. Seller accounts and unverified callers cannot read the log. It has no edit or delete API. Client collection accepts only fixed action/control/context enums and bounded metadata, rejects unrelated paths and cross-origin requests, and is rate limited. Actor identity is resolved on the server, never trusted from an event payload.

Passwords, verification codes, cookies, authorization headers, authentication links/query parameters, raw IP addresses, document contents, filenames and arbitrary error messages/stacks are excluded. Marketplace conversation text is now retained on the owner's explicit request, with known credential/token patterns and hidden system context redacted. Identity logging observes only the route, status, timing and verified server identity. Existing authentication bodies and responses are never retained in the activity table.

Completed account/listing research stores a curated immutable recommendation snapshot (summary, findings, source evidence, model/policy, timestamp and advisory authority) under the related user account. Reviewing current reports does not rerun research, change account access or approve listings. Existing current reports retain their existing business-record lifecycle; the activity-log snapshot has its own retention.

The log uses a separate SQLite Durable Object table (`exchange_activity`) with indexed timestamps, event IDs, conversation/account keys and a monotonically increasing sequence. Conversation details are limited to the latest 100 exchanges, and each exchange is bounded to 5,000 user characters and 12,000 assistant characters. Business-state snapshot writes cannot overwrite it. Retention is **90 days or the latest 100,000 events, whichever is smaller**; reads exclude expired events and writes prune expired/excess rows. Retrieval returns at most 100 events per page (UI default 50). A logging-storage failure must not replay, block or change a business operation; the response marks activity persistence unavailable when possible. Existing conservation capture reads remain outside activity/schema writes. No account/listing data migration is required.

## Verification

`activity-content.test.mjs` covers John's pre-hydration attribution, stale account claims, transcript confidentiality/redaction, current reports and historical snapshot invariance. `activity-log.test.mjs` checks attribution, permissions, filtering, pagination, rollback isolation, retention, redaction, rate limits and stale identity handling. `activity-runtime.test.mjs` runs the real entry point, SQLite Durable Object and private authentication-result logging in workerd. `activity-browser.mjs` checks the built administrator workspace at desktop/mobile widths, filters/pagination/details/empty/error/retry states, and isolated browser collection/scope/privacy behavior. Production browser acceptance intercepts all private requests into disposable fixtures and permits only public asset GETs to leave the fixture.
