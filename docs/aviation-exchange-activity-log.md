# Aviation Exchange activity log

The administrator workspace has a read-only **Activity log** section. It covers the Aviation Exchange marketplace, its account and listing APIs, authentication/security operations, customer support, administrator operations, completed Jerry research, and browser interactions on `/aircraft-for-sale` and its listing pages. The rest of the website is excluded. Existing moderation audit records retain their original behavior; historical browser activity cannot be reconstructed. Logging starts at deployment.

## Fields and troubleshooting

Events contain a server timestamp, account ID/email when verified, action, result, source, HTTP status and duration when applicable, a server-generated request ID, route template, related listing/account/ticket ID, and selected structured operation details. An expandable row shows the full UTC timestamp and request ID. Table times use the administrator's local timezone; date filters use UTC. Search accepts account email/ID, action, request ID or record ID. Result/source filters, date bounds, refresh and cursor pagination are available.

Server requests carry `X-RWAS-Request-ID` and `X-RWAS-Activity-Recorded`. Authentication responses carry a request ID; their metadata is queued through the private service binding. A failed request is logged independently of business rollback. A server success means that HTTP operation succeeded: it is not proof of a downstream email's delivery, a completed aircraft transaction, or a listing's approval. A `changes` detail on a failed request describes attempted operations; the failure result remains authoritative. Browser events are explicitly labeled as browser reported; they never constitute an authoritative approval or completed mutation.

Browser tracking records page views/leaves, control selection, field changes without contents, form submissions, draft step transitions, Jerry chat transport results and network/client errors. It is mounted only on marketplace pages, stops outside the marketplace after client navigation, and sends small bounded same-origin batches. Browser collection requires JavaScript and connectivity, uses a bounded in-memory queue and cannot guarantee delivery after abrupt process termination. No keystrokes or message bodies are collected. Account references captured at event time are checked against the current verified server identity; unmatched queued events remain anonymous after an account switch.

## Access, data handling and storage

`GET /api/aircraft-sale/staff/activity` requires the existing current verified administrator identity, including the established MFA policy. The legacy `/admin/activity` route requires the scoped account administrator. Seller accounts and unverified callers cannot read the log. It has no edit or delete API. Client collection accepts only fixed action/control/context enums and bounded metadata, rejects unrelated paths and cross-origin requests, and is rate limited. Actor identity is resolved on the server, never trusted from an event payload.

Passwords, verification codes, cookies, authorization headers, authentication links/query parameters, raw IP addresses, message/description contents, document contents, filenames and arbitrary error messages/stacks are excluded. Identity logging observes only the route, status, timing and verified server identity. Existing authentication bodies and responses are never retained in the activity table.

The log uses a separate SQLite Durable Object table (`exchange_activity`) with an indexed timestamp and monotonically increasing sequence. Business-state snapshot writes cannot overwrite it. Retention is **90 days or the latest 100,000 events, whichever is smaller**; reads exclude expired events and writes prune expired/excess rows. Retrieval returns at most 100 events per page (UI default 50). A logging-storage failure must not replay, block or change a business operation; the response marks activity persistence unavailable when possible. Existing conservation capture reads remain outside activity/schema writes. No account/listing data migration is required.

## Verification

`activity-log.test.mjs` checks attribution, permissions, filtering, pagination, rollback isolation, retention, redaction, rate limits and stale identity handling. `activity-runtime.test.mjs` runs the real entry point, SQLite Durable Object and private authentication-result logging in workerd. `activity-browser.mjs` checks the built administrator workspace at desktop/mobile widths, filters/pagination/details/empty/error/retry states, and isolated browser collection/scope/privacy behavior. Production browser acceptance intercepts all private requests into disposable fixtures and permits only public asset GETs to leave the fixture.
